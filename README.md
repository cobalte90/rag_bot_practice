# PostgresHelperBot

`PostgresHelperBot` — учебный чат-ассистент, который отвечает на вопросы по документации PostgreSQL 18 с помощью RAG-пайплайна, гибридного поиска и Mistral API. Пользователь задает вопрос на русском языке, система ищет релевантные фрагменты в англоязычной официальной документации PostgreSQL, а затем формирует краткий ответ на русском и показывает короткую цитату из источника на английском.

## Почему этот проект полезен

- отвечает по официальной документации PostgreSQL 18, а не по случайным источникам;
- умеет работать в cross-lingual сценарии: вопрос на русском, документация на английском;
- использует гибридный retrieval: semantic search + keyword search;
- показывает источник ответа: файл, страницы, `chunk_id`;
- подходит как учебный MVP для демонстрации RAG-архитектуры, Docker-запуска и LLM-интеграции.

## Что умеет бот

- принимает вопросы на русском языке в чате;
- ищет релевантные фрагменты по документации PostgreSQL 18;
- отвечает на русском языке кратко и по делу;
- вставляет короткую английскую выдержку из найденного контекста;
- честно сообщает, если в найденных фрагментах недостаточно информации;
- показывает источник: файл, страницы и идентификатор фрагмента.

Примеры вопросов:

- Что такое индекс в PostgreSQL?
- Как работает `EXPLAIN`?
- Чем `DELETE` отличается от `TRUNCATE`?
- Как создать внешний ключ?
- Что такое `VACUUM`?
- Как сделать backup базы?
- Какие типы данных есть в PostgreSQL?

## Демонстрационный сценарий

1. Пользователь пишет вопрос в чат.
2. Бот загружает уже готовый retrieval-индекс.
3. Гибридный retriever ищет релевантные чанки в документации.
4. В Mistral API передаются только вопрос, системный промпт и найденный контекст.
5. Пользователь получает:
   - краткий ответ на русском;
   - короткую выдержку из документации на английском;
   - явную ссылку на источник.

## Архитектура

```text
Пользователь
   ↓
Chat Interface (aiogram)
   ↓
Hybrid Retriever
   ├─ FAISS (semantic search)
   └─ BM25 (keyword search)
   ↓
Top-K chunks + metadata
   ↓
Mistral API
   ↓
Ответ на русском + английская выдержка + источник
```

### Архитектурные блоки

**1. Конфигурация**

Файл: `src/config.py`

- читает `.env`;
- валидирует параметры;
- хранит пути к данным и индексам;
- задает значения по умолчанию для retrieval и LLM.

Почему это важно:

- секреты не хардкодятся;
- проект одинаково работает локально и в Docker;
- легко менять модель, веса поиска и параметры чанкинга.

**2. Загрузка документов**

Файл: `src/document_loader.py`

- ищет документы в `data/raw/`;
- поддерживает `pdf`, `txt`, `docx`;
- для PDF извлекает текст постранично, чтобы сохранять номера страниц.

Почему это важно:

- страницы нужны для честной ссылки на источник;
- один и тот же код можно расширять под новые форматы документов.

**3. Очистка и чанкинг текста**

Файлы: `src/text_cleaner.py`, `src/chunker.py`

- убирают шумы форматирования;
- сохраняют технические термины и SQL-синтаксис;
- режут текст на чанки с overlap;
- сохраняют метаданные каждого фрагмента.

Почему выбрано именно так:

- слишком длинные фрагменты ухудшают retrieval;
- слишком короткие ломают смысл;
- overlap помогает не терять информацию на границах чанков.

**4. Embeddings**

Файл: `src/embeddings.py`

Используется `intfloat/multilingual-e5-small`.

Почему выбрана эта модель:

- пользователь спрашивает по-русски, документация на английском;
- multilingual retrieval лучше обычных англоязычных эмбеддингов для cross-lingual matching;
- модель достаточно компактная и быстрая для учебного MVP.

Что важно в реализации:

- для документов используется префикс `passage:`;
- для запросов используется префикс `query:`;
- embeddings считаются батчами;
- модель загружается один раз и повторно используется из локального cache.

**5. Векторный и keyword поиск**

Файлы: `src/vector_store.py`, `src/keyword_search.py`

- `FAISS` отвечает за semantic search по embedding-векторам;
- `BM25` отвечает за точный лексический поиск терминов.

Почему нужен гибридный подход:

- semantic search хорошо понимает естественные русские вопросы;
- BM25 хорошо ловит точные термины вроде `EXPLAIN`, `VACUUM`, `TRUNCATE`, `GROUP BY`, `CREATE TABLE`;
- вместе они работают устойчивее, чем любой из методов по отдельности.

**6. Hybrid Retriever**

Файл: `src/retriever.py`

Алгоритм:

1. Строится embedding вопроса.
2. Выполняется поиск в FAISS.
3. Выполняется поиск в BM25.
4. Оба score нормализуются.
5. Результаты объединяются по `chunk_id`.
6. Вычисляется итоговый score.
7. Возвращаются `top-k` релевантных чанков.

Формула:

```text
final_score = VECTOR_WEIGHT * vector_score + KEYWORD_WEIGHT * keyword_score
```

Преимущество:

- retrieval прозрачен и настраиваем;
- можно отдельно тестировать качество поиска без чат-интерфейса и без LLM.

**7. LLM-слой**

Файлы: `src/prompts.py`, `src/llm_client.py`

- Mistral API получает системный промпт, вопрос и найденные чанки;
- системный промпт принуждает модель отвечать только по контексту;
- модель должна обязательно вернуть английскую выдержку и указать источник.

Почему это важно:

- снижается вероятность галлюцинаций;
- ответ становится проверяемым;
- проект выглядит как настоящий retrieval-grounded assistant, а не просто чат-бот.

**8. Чат-интерфейс**

Файл: `src/bot.py`

Используется `aiogram`.

Поддерживаются команды:

- `/start`
- `/help`
- `/sources`
- `/status`

Почему это удачный выбор для MVP:

- чатовый интерфейс удобен для быстрой демонстрации проекта преподавателю;
- не нужен отдельный web-интерфейс;
- `aiogram` хорошо подходит для асинхронной обработки сообщений.

## Преимущества проекта

### 1. Честный RAG, а не “просто LLM”

Бот не должен отвечать из внешних знаний модели. Ответы строятся только на найденных фрагментах документации.

### 2. Проверяемость ответа

Пользователь видит не только объяснение, но и:

- короткую цитату из документации на английском;
- файл;
- страницы;
- идентификатор фрагмента.

### 3. Поддержка двух языков

Система решает практическую задачу: пользователь общается на русском, а документация остается на английском.

### 4. Быстрый онлайн-режим

PDF читается только во время индексации. Во время работы бота используются уже готовые индексы.

### 5. Прозрачная структура

Проект разделен на независимые слои:

- ingestion;
- retrieval;
- generation;
- чатовый интерфейс;
- конфигурация;
- тесты.

Это делает код понятным и расширяемым.

### 6. Готовность к демонстрации

Проект можно:

- запустить локально;
- запустить через Docker;
- показать в чате;
- описать в отчете по практике;
- загрузить на GitHub как законченный MVP.

## Ограничения текущего MVP

- бот отвечает только по локально проиндексированной документации;
- история диалога не хранится;
- качество retrieval зависит от качества извлечения текста из PDF;
- нет отдельного reranker-а поверх первичного retrieval;
- нет автоматического обновления документации;
- возможны ошибки LLM, поэтому источник показывается явно.

## Возможности для развития

### Улучшение retrieval

- добавить reranking;
- улучшить query expansion;
- привязать чанки к главам и разделам документации;
- использовать evaluation-набор вопросов для подбора весов retrieval.

### Улучшение качества ответа

- добавить отдельный режим генерации SQL-примеров;
- добавить режим “объясни простыми словами”; 
- добавить более строгую пост-обработку ответа и валидацию формата.

### Поддержка истории диалога

- хранить последние сообщения пользователя;
- поддержать follow-up вопросы;
- сделать память диалога ограниченной по длине.

### Расширение базы знаний

- добавить несколько версий PostgreSQL;
- добавить документацию по `pg_dump`, `pg_restore`, `psql`, настройке сервера;
- добавить вспомогательные справочные материалы.

### Интерфейс и эксплуатация

- перейти с polling на webhook;
- добавить мониторинг и метрики;
- кэшировать ответы;
- сделать web-интерфейс;
- добавить CI/CD.

## Быстрый старт локально

### 1. Создать виртуальное окружение

```bash
python -m venv .venv
```

Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

Linux/macOS:

```bash
source .venv/bin/activate
```

### 2. Установить зависимости

```bash
pip install -r requirements.txt
```

### 3. Создать `.env`

Linux/macOS:

```bash
cp .env.example .env
```

Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

Заполните минимум:

- `TELEGRAM_BOT_TOKEN`
- `MISTRAL_API_KEY`

### 4. Положить документацию

Файл документации должен лежать по пути:

```text
data/raw/postgresql-18-US.pdf
```

### 5. Построить индекс

```bash
python scripts/ingest.py
```

### 6. Проверить retrieval

```bash
python scripts/test_retrieval.py
```

Для отладки:

```bash
python scripts/test_retrieval.py --debug
```

### 7. Запустить бота

```bash
python main.py
```

## Запуск через Docker

### Базовый запуск

```bash
docker compose up --build
```

Что произойдет:

1. Контейнер проверит наличие индекса через `scripts/ensure_index.py`.
2. Если индекс отсутствует, он будет построен автоматически.
3. После этого стартует чат-приложение.

### Повторная индексация в Docker

```bash
docker compose run --rm bot python scripts/ingest.py
```

### Проверка retrieval в Docker

```bash
docker compose run --rm bot python scripts/test_retrieval.py
```

## Docker-устройство проекта

В `docker-compose.yml` монтируются volume:

- `./data/raw:/app/data/raw`
- `./data/index:/app/data/index`
- `./data/processed:/app/data/processed`
- `./.cache:/app/.cache`

Преимущество такого решения:

- индексы сохраняются между перезапусками;
- модель Hugging Face кэшируется локально;
- не нужно каждый раз заново скачивать все артефакты.

## Формат ответа бота

Бот старается отвечать в таком виде:

```text
Ответ:
<краткий ответ на русском>

Выдержка из документации:
"<короткая английская выдержка из найденного контекста>"

Источник:

* postgresql-18-US.pdf, стр. 598-599, фрагмент postgresql-18-US_chunk_1717
```

Если контекст слабый, бот должен честно ответить, что информации недостаточно.

python -m pytest

Минимально покрыто:

- чанкинг;

## Секреты и публикация

- `.env` не должен попадать в git;
- реальные ключи нельзя хранить в репозитории;
- `data/index/`, `data/processed/`, `.cache/` и служебные артефакты не коммитятся;
- при желании PDF можно хранить в репозитории, если размер допустим, либо скачивать вручную перед запуском.

## Итог

`PostgresHelperBot` — это компактный, но полноценный учебный RAG-проект: с ingestion-пайплайном, гибридным retrieval, LLM-генерацией, чат-интерфейсом, Docker-запуском и тестами. Проект хорошо подходит для отчета по практике, демонстрации преподавателю и дальнейшего развития в сторону более серьезного документационного ассистента.
